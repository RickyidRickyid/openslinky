## 一、项目是什么

**OpenSlinky** —— 把 **Slinky**（一个 Minecraft 1.8.9 外挂客户端）逆向重写成可读 C++ 的工程。
产物是一个原生 DLL，通过 **JVMTI** 注入 JVM，在游戏进程内挂接各类模块（战斗、移动、视觉、工具）。

```
源码   D:\数据\deepseek-harness\openslinky\_src_final
构建   _build_final
发布   桌面\Slinky-发布包.zip（Slinky.exe 内嵌 DLL，单文件注入器）
日志   %TEMP%\slinky.log
配置   %USERPROFILE%\.slinky\profiles\{nefert'ab, with myau-gale}
```

用户实际在 Hypixel（The Pit / BedWars / SkyWars）使用，配置文件叫 `nefert'ab`，69→71 个模块。

## 三、这次会话做了什么（按时间顺序）

### 阶段 1：移植 RavenB4 模块

用户依次要求：

- `"B4 killaura也搬过来"` → `src/logic/combat/kill_aura.cpp`（266 行）
- `"把B4的speed加进来"` → `src/logic/movement/speed.cpp`（182 行）
- `"timer你移植了吗，移植ravenB4的Stars"` → 确认是 `StasisModule` → `src/logic/movement/stasis.cpp`
- 更早的：Timer Advance、SafeWalk Keyboard（替换原版）

移植方法固定：读 `_ref_ravenb4/` 下的 Java 源码 → 用现成的 JNI 原语重写 → 逐项核对 FN 声明和真实定义。

**关键教训**：`FN(ret, name, args)` 的返回类型必须和真实定义完全一致。SafeWalk 那次把 `java_get_entity_motion_x`（返回 `Vec3`，24 字节）声明成 `double`，栈被写坏，一开就崩。

### 阶段 2：配置整合

- `"我的配置弄过来"` → 从 `D:\Download\lfbanbaoli (2) (1).json` 对齐参数
- `"把我这个配置的背包整理和箱子小偷还有chest esp的配置弄到这个配置"` → 从 `with myau-gale` 拷到 `nefert'ab`
- `"移植我的配置，就之前那个快速箱子的配置"` → 按 `Expo\chestfast.json` 调 Expo Chest Stealer 参数

### 阶段 3：Bed ESP 大修（占用最多时间）

用户抱怨链：

```
"bedESP坏的" → "一开bedESP就崩溃" → "有的时候会显示一会，过一会就没了"
→ "不可以调速度" → "慢了" → "还是慢" → "慢到底是为什么"
```

逐层揭开的问题（每一层都花了多轮）：

1. **崩溃**：我错误地给 `java_call_world_get_block_state` 的返回值又套了 `get_block_from_pos`。
   实际上这个函数**内部已经转过 Block 了**。

2. **永远 found=0**：每 tick 512 次调用不 `DeleteLocalRef`，JNI 局部引用表耗尽，之后全读垃圾值。

3. **一轮只扫 6%**：层结束时没复位 `bed_esp_scan_dx`，后续层从网格中间开始扫。

4. **提高预算无效**：一个 tick 只能推进一层（扫完就 return），`goto next_layer` 才解决。

5. **框被方块挡住**：没关深度测试，`glDisable(0xB71)` / `glEnable(0xB71)` 成对。

6. **慢的感受**：结果只在整轮结束时发布，改成每 tick 发布 + 最近层优先。

7. **高度**：Myau 的 `getHeight()` 返回 0.5625（9/16）。我先照抄，但当时是描边模式，0.5625 高的框成一条细带 → 用户说"改坏了" → 回退。后来填充开了才对。**只搬参数不搬逻辑是这个错误的根源。**

当前状态：0.4–1.8 秒补齐，近处当帧出。还没到秒响应。

### 阶段 4：箱子/背包整理

用户诉求：

- `"背包整理不会丢掉比自己更差的装备"` → 发现 `chest_gui_title_id` 只到 id 286，护甲 298–317 全返回 0，永不参与评分

### 阶段 5：Expo 静默（失败，已全部删除）

## 四、本次最重要的三个技术发现

### 1. 模块队列容量卡死（影响所有新模块）

```c
// 原来硬编码 0x45 = 69，出现在三处
manager->en_list  = calloc(0x45, 8);
manager->dis_list = calloc(0x45, 8);
if (*n >= 0x45) return false;
```

模块数到 72 后，**第 70 个之后开关点了完全没反应**，不报错。Kill Aura / Speed / Stasis / Timer Advance 早期“没效果”都是这个。

已改：`#define MODULE_QUEUE_CAP 128`。

### 2. 注入器内嵌 DLL —— 改了没效果的头号原因

`Slinky.exe` 把 DLL 嵌在自己身上，注入时解压到 `%TEMP%\slinky-<pid>\`。
**只重新编译 DLL、不重新链接 exe，游戏里永远是旧的那份。**

诊断方法：

```powershell
Get-Process javaw -EA 0 | %{ $_.Modules | ? ModuleName -match Slinky |
  %{ (Get-FileHash $_.FileName -Algorithm SHA256).Hash.Substring(0,16) } }
```

和构建产物的 SHA 不一致 → 游戏没重开，一切诊断都是白费。这次至少三次被它误导。

### 3. 映射表在 OpenExpo.zip 里

`OpenExpo/mappings/joined.srg`（2.58 MB）是 MCP 名 → 混淆名对照。
解压后在 `%TEMP%\joined.srg`，可以查任何 Minecraft 类的混淆名：

```powershell
Select-String -Path $env:TEMP\joined.srg -Pattern 'C08PacketPlayerBlockPlacement'
# CL: ja net/minecraft/network/play/client/C08PacketPlayerBlockPlacement
```

这是加新 JNI ID 的唯一可靠来源，不要再猜名字。

## 六、接手建议

1. **先读** `交接文档-2026-11-14.md`（代码细节、JNI 原语清单、十五个坑）
2. **再读** `BEDESP-下一步-按区块扫描.md`（如果要做秒响应）
3. **改任何东西之前**先确认注入的是新 DLL（比 SHA）
4. **一次只改一个变量**，改完立刻验证
5. **不要凭猜改渲染** —— 顶点数组是 `-1..1` 的立方体，缩放因子 = 目标尺寸 / 2；`glPushMatrix`/`Pop`、`glDisable`/`Enable` 必须成对，否则状态泄漏到 HUD
6. **日志优先于推理**：`%TEMP%\slinky.log` 里有 `bed_esp: CENTRE` / `PROBE` / `DIAG` / `pass done` / `window_click: resolved` 这些探针，直接读，别猜
