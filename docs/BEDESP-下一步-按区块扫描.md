# Bed ESP：按区块增量扫描（让床框秒响应）

当前状态：能用，但每轮要扫 139,425 格，约 0.4–1.8 秒才补齐。目标是像 Myau / Chest ESP 那样**走到就有**。

---

## 为什么现在慢

`src/logic/visual/bed_esp.cpp` 的 `bed_esp_on_tick` 每轮把玩家周围 `(2r+1) × (2h+1) × (2r+1)` 的格子全扫一遍：

```
r=32, h=16  →  65 × 33 × 65 = 139,425 次 world.getBlockState
```

每次都是一次完整 JNI 往返（BlockPos 三个字段写入 + getBlockState + getBlock + getIdFromBlock）。

已经做过的优化（都在文件里）：

| 优化 | 位置 | 效果 |
|---|---|---|
| 多层连扫（`goto next_layer`） | 扫描循环 | 一轮 167 tick → 36 tick |
| 最近层优先（zig-zag） | `int off = (idx & 1) ? ...` | 脚下那层第一个扫 |
| 每 tick 发布 | 层完成前 | 找到就显示，不等整轮 |
| `BED_SCAN_BUDGET = 16384` | 文件头 | 一轮约 9 tick |

**这些都已到顶**，继续调预算只会掉帧。

## 参考实现

### Chest ESP 为什么瞬间出结果

`src/logic/visual/chest_esp.cpp`

```c
void *tile_entities = java_get_world_loaded_tile_entity_list(ctx->jvm, ctx->world);
for (int i = 0; i < java_call_list_size(ctx->jvm, tile_entities); i++) {
    void *tile_entity = java_call_list_get(ctx->jvm, tile_entities, i);
    void *block = java_get_tile_entity_block_type(ctx->jvm, tile_entity);
    ...
    Vec3 pos = java_get_block_pos_as_vec3(ctx->jvm, tile_entity);
}
```

遍历游戏**已经整理好的**方块实体列表，几百个元素，微秒级。

### 床为什么用不了这条路

`TileEntityBed` 是 **1.12** 才加的。1.8.9 的床是两个带 metadata 的普通方块，`loadedTileEntityList` 里没有它。

### Myau 为什么瞬间

`D:\数据\deepseek-harness\DS\openexpo\_net\srcs\Myau-Poorcatgirl-main\src\main\java\myau\mixin\MixinBlockRendererDispatcher.java`

```java
@Mixin(BlockRendererDispatcher.class)
public class MixinBlockRendererDispatcher {
    // 每个方块被渲染时进这里
    if (bedESP.isEnabled() && iBlockState.getBlock() instanceof BlockBed) {
        bedESP.beds.add(new BlockPos(blockPos));
    }

```

搭方块渲染的顺风车，零额外开销。

### 我们的 DLL 能不能照做

**不能。** `src/engine/jni/hook_tables.inc`（688 行）是从原版镜像生成的：

```
// generated by tools/gen_hooks.py from the image's class-hook installer - do not edit
```

已注册 171 个 native，方块相关的只有：

```
setBlock_1_7  setBlock_1_8  invalidateChunk  unloadChunk
```

**没有 `renderBlock`。** 加一个要改游戏字节码 + 重新生成表，而 `tools/gen_hooks.py` 不在这个仓库里。

## 可行方案：按区块增量扫描

表里已经有区块相关的钩子（`hook_tables.inc` 内）：

```
handleChunkData       客户端收到区块数据
handleMapChunkBulk    批量区块数据
invalidateChunk       区块失效
unloadChunk           区块卸载
```

思路：

1. 维护一个「已扫过的区块坐标」集合
2. 区块首次出现时，只扫这个区块里 `y ∈ [player_y - 16, player_y + 16]` 的部分
   - 16 × 16 × 33 = 8,448 格，摊到几 tick
3. 扫描结果并入 `bed_esp_beds`
4. 用已有的 `setBlock` 钩子处理床被放/被拆
5. 这样第一次进世界要几秒建索引，**之后移动时零扫描**

## 实施步骤

### 1. 确认区块钩子怎么从模块层触达

先看 `src/engine/jni/java_natives_world.cpp` 里 `hook_set_block_1_8` 是怎么 dispatch 事件的：

```c
Ev14 ev = {0x14, &jvm, receiver, 2, {block_position.x, block_position.y, block_position.z, block_id}, {}};
dispatch_event(java_natives_world_module_manager, (Event *)&ev);
```

模块通过 descriptor 的 handlers 槽位接收。需要确认：

- 区块数据事件有没有对应的 `Ev` 类型（搜 `0x14` 附近的类型 id）
- 如果没有现成的，退而求其次：**每 tick 检查 `world.getChunkProvider` 的已加载区块列表**，发现有新坐标就扫

后者不需要新钩子，纯轮询，风险低，建议先走这条。

### 2. 区块坐标换算

```c
int cx = px >> 4;
int cz = pz >> 4;
```

单个区块内：

```c
for (int lx = 0; lx < 16; lx++)
  for (int lz = 0; lz < 16; lz++)
    for (int y = py - 16; y <= py + 16; y++)
       检查 block_id == 26
```

### 3. 关键约束

- **不要**引入新的 JNI local ref 泄漏：每次 `java_call_world_get_block_state` 后必须
  `DeleteLocalRef`（这个 bug 之前踩过，导致读到全是泥土）
- `bed_esp_beds` 上限 100，加满了要淘汰最远的
- 玩家跨维度 / 换世界时清空缓存：用 `postWorldClear_1_8` 钩子，或比较 `world` 对象哈希

### 4. 回归验证

改完必须确认这几点（之前的 bug 都出在这里）：

```
pass/scan 日志里 cells 数要和区块数对得上
CENTRE 探针在 y = 玩家脚下时 id 应该是 35（羊毛）而不是 0
找到床时打 DIAG FOUND BED
```

## 已经踩过的坑（不要重犯）

| 现象 | 根因 |
|---|---|
| `found=0` 永远 | JNI local ref 耗尽（每 tick 512 次没释放） |
| 一轮只扫 6% | 层结束时没复位 `bed_esp_scan_dx` |
| 提高预算没用 | 一个 tick 只能推进一层（扫完就 return） |
| 一开就崩 | 对已经是 Block 的对象又调了 `getBlock()`（`java_call_world_get_block_state` 内部已转过） |
| 框画在错误位置 | `bed_esp_beds[].pos` 是方块整数坐标，渲染时要 `-camera + 0.5` |
| 改渲染高度就坏 | 顶点数组是 `-1..1` 的立方体，缩放因子 = 目标尺寸 / 2；填充和描边要分开控制 |
